# v1.2 graph-intelligence handoff

**Date:** 2026-06-08  
**Milestone:** [v1.2.0](https://github.com/kwad77/pincher/milestone/102)  
**ADR:** [ADR-0004: v1.2 Pincher-native graph intelligence](../adr/0004-v1.2-pincher-native-graph-intelligence.md)

## Direction

v1.2 should turn Pincher's existing indexed graph and `_meta` envelopes into higher-leverage artifacts for humans, agents, and pincher-router.

The framing is deliberately **Pincher-native graph intelligence**, not Graphify parity. We can learn from the broad idea of persistent graph-derived orientation, but the implementation must preserve Pincher's own secret sauce:

- deterministic extraction and source provenance;
- low-latency MCP/HTTP/CLI workflow tools;
- freshness and binary/schema drift diagnostics;
- `trace`, `changes`, `context_for_task`, and other edit-loop primitives;
- `_meta` fields for cost, latency, complexity tier, warnings, and capabilities;
- falsifiable savings/impact reporting that pincher-router can trust.

## Product boundary

### We are building

- reportable architecture evidence from the existing Pincher index;
- rationale/design-intent navigation with line-span provenance;
- actionable hotspots and surprising-edge triage;
- savings/work-impact reporting based on raw `_meta` fields;
- next-best-call guidance that agents can execute and router loops can measure;
- export/provenance hardening for external analysis.

### We are not building

- a clone of Graphify or a parity checklist;
- a default LLM semantic extraction pipeline for v1.2;
- unsupported "N.x token reduction" marketing claims;
- a dashboard-first graph visualization without report/API evidence underneath;
- MCP/tool-surface compression as a cost-reduction track.

## Recommended implementation sequence

### Slice 1 — report skeleton from existing data

Start with #1912. Implement the smallest useful `pincher report` that composes existing evidence:

1. project stats / health / freshness;
2. architecture entry points and hotspots;
3. surprising connections;
4. rationale node count and samples if available;
5. suggested next calls as prose first, then structured in #1917.

This should avoid new DB schema unless a missing provenance field is discovered.

### Slice 2 — make report sections first-class

Implement #1913, #1914, and #1915 as reusable internals/surfaces so `pincher report` does not own all logic.

Acceptance pressure:

- raw scoring inputs for hotspot rank;
- source spans for rationale and example surprising edges;
- deterministic reasons for triage output;
- fixture/golden tests.

### Slice 3 — savings/work-impact evidence

Implement #1916 after report scaffolding exists. The key rule: **no unsupported aggregate claims**.

Required behavior:

- expose raw token inputs and baseline method;
- derive formulas in output;
- report missing fields/schema gaps;
- separate recent-window data from stale historical logs;
- make output consumable by pincher-router.

### Slice 4 — next-best calls and router leverage

Implement #1917 by making follow-up suggestions structured:

```json
{
  "tool": "trace",
  "args": {"id": "...", "direction": "callers"},
  "why": "Top hotspot with high fan-in; inspect blast radius before editing."
}
```

Validate against actual tool schemas so suggestions never include invalid arguments.

### Slice 5 — export/dashboard polish

Implement #1918 and #1858 after evidence contracts stabilize.

The dashboard should visualize Pincher evidence, not create a second product center of gravity. Export should preserve provenance, schema version, confidence, and indexed timestamp.

## Release acceptance criteria

v1.2 is ready when:

- a user can run one command and get a useful project report;
- report claims are source-grounded and missing data is explicit;
- rationale/hotspot/surprising-edge surfaces are reusable and tested;
- savings reports are falsifiable and refuse unsupported claims;
- next-best-call suggestions are structured and schema-valid;
- release notes avoid clone/parity language and explain Pincher's routing/provenance advantage.

## Risks

| Risk | Mitigation |
|---|---|
| Dashboard/UI sprawl delays release | Keep #1858 downstream of report/API evidence. |
| Clone optics | Use ADR-0004 language in docs/release notes; avoid parity checklists. |
| Savings overclaiming | Require baseline_method/raw fields; emit schema gaps. |
| Noisy graph analytics | Start with deterministic, explainable scoring before community/inference. |
| Stale index creates bad report | Include freshness and binary/schema drift in every report. |

## First concrete task for an agent

Start #1912 with TDD:

1. Use Pincher to inspect existing `architecture`, `health`, `stats`, and CLI command patterns.
2. Add a fixture/golden test for `pincher report --format markdown`.
3. Implement a minimal report generator from existing service methods.
4. Verify with focused tests, then `mcp_pincher_changes` before final status.

Do not begin with dashboard rendering or new LLM extraction.
