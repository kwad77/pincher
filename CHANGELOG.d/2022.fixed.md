**Short writes survive a concurrent index's cross-process writer lock — bounded retry instead of hard SQLITE_BUSY ([#2022](https://github.com/kwad77/pincher/issues/2022)).** In the production-default topology (the systemd HTTP daemon and Claude Code's stdio MCP server both bound to one `~/.pincher-data`), SQLite's WAL mode allows exactly one writer across *all* processes. The DSN's `busy_timeout(5000)` only makes a single statement wait up to 5s — but a force-reindex holds the writer far longer, so the *other* process's short writes (loop-checkpoint append, ADR set/delete) hard-failed with persistent `database is locked (5) (SQLITE_BUSY)` (live repro: 4× over ~1 min on POST `/v1/adr`). The short write paths are now wrapped in a new `retryBusy` helper: context-bounded (30s hard cap via internal `WithTimeout`, honouring any tighter caller deadline) exponential backoff (25ms → 2s) with full jitter, retrying only on SQLITE_BUSY and surfacing any other error immediately. A long index transaction stays *unwrapped* — it is the writer everyone waits on, so retrying it would deepen contention. Sustained contention is observable: a single stderr line fires once a short write passes 4 retries. This turns the hard failure into bounded latency — graceful degradation. Pinned by `TestRetryBusy_*` (succeeds-immediately, retries-then-succeeds, non-busy-returns-immediately, respects-context-deadline).
