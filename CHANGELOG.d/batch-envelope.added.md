**New `batch` tool — one envelope, N read-only sub-queries under a shared token budget (loop-substrate).** A loop agent that needs several probes per iteration (a search, a context read, a caller trace) previously paid the full per-call ceremony — watermark, capabilities slice, transport round-trip, stats accumulation — once *per answer*. The A/B benchmark behind the loop-substrate work showed exactly this shape deciding every round: per-call ceremony vs batched greps. `batch` accepts up to 12 `{tool, args}` sub-queries over the read-only set (`search`, `symbol`, `symbols`, `context`, `trace`, `query`, `neighborhood`, `changes` — no writers, no batch-in-batch) and answers them in order inside ONE envelope: a shared `max_tokens` budget (default 4000) is spent in input order with later sub-queries skipped (`skipped:"budget_exhausted"` + `budget_truncated` warning) once exhausted; budget-aware sub-tools (`context`, `symbols`) inherit the remaining budget; each entry ships a slim per-entry `_meta` (`empty_reason` / `tokens_used` / `warnings_v2` only) while the outer envelope carries the single full `_meta`. Sub-errors are isolated — a bad symbol ID yields a per-entry `error` field plus a `batch_sub_errors` warning naming the failed indexes, and the rest of the batch completes. Session stats count the batch as exactly one call (sub-calls are `_nested` and skip accumulation) with `tokens_saved` honestly summed from the sub-calls' own baselines. Top-level `project` merges into every sub-query that doesn't set its own.
