**`verify_change` tool — the loop's post-edit gate in ONE call (loop-substrate PR-10).** The post-edit checkpoint of an agent loop asks three questions — "did my edit do what I planned, what do I run, what broke" — and previously paid three-plus calls (a `changes` run, a mental diff against a `plan_change` output that's long gone from the context window, and a `dead_code` sweep nobody remembers). `verify_change` answers all three in one envelope: (1) the `changes` blast-radius analysis over `scope` (unstaged/staged/all/base:<branch>), via a shared `analyzeChanges` core extracted from the handler so the two tools can't drift; (2) `tests_to_run` ranked by overlap; (3) predicted-vs-actual blast radius — `plan_change` now stashes each run's FULL depth-1 caller set plus the index generation in a bounded in-memory plan cache (newest 32), and `verify_change target=<same>` reports `plan_comparison.{predicted_callers, actual_impacted, unpredicted_impact}` with `warnings_v2 code=unpredicted_impact` when the edit reached direct callers the plan never saw, `code=plan_stale` when the index generation moved between plan and verify (staleness instead of a bogus diff), and `code=no_plan_cached` (info) with the comparison absent when no plan exists; (4) `possibly_orphaned` — the `dead_code` SQL path restricted to the changed files (new `GetDeadCodeForFiles`, same query, same carve-outs), reporting symbols with zero inbound edges now, labelled advisory `possibly_orphaned_by_change` and limited to Functions — Methods are excluded because the static call graph is dispatch-blind for interface calls. `max_tokens` bounds the envelope with a deterministic degradation order (bulk lists first; summary counts always ship; `code=budget_truncated` names the cuts). Closes the loop-substrate plan→edit→verify contract: `plan_change` before the edit, `verify_change` after, `loop checkpoint` to record the verdict.
