**`batch` chain mode — server-side pipelining so intermediates never cross the token envelope (loop-substrate M13).** When sub-query N's input is sub-query M's output (the canonical loop step: search → context on the top hit), the agent previously ferried the intermediate ID through its own context window and paid for it twice. A sub-query can now declare `from: {query: <lower index>, select: "top_id"|"ids"|"files", into: "<arg key>"?}` and the server splices the selection into its args locally. Named selectors only (v1 scope discipline — no path language): `top_id` (first result's stable symbol id across search/trace/context shapes), `ids` (all result ids, deduped, capped at 20 with a `chain_selector_trimmed` warning), `files` (distinct file_path values, capped at 10). `into` defaults to `"id"` for context/symbol/trace and `"ids"` for symbols; multi-value selects pair with `symbols`' `ids` arg only (fan-out deliberately not implemented in v1). Execution stays strictly declaration-order: forward references rich-error at validation time before any execution; an errored/skipped/empty upstream yields `skipped:"upstream_empty"` — never a guessed call — and chain segments respect the shared `max_tokens` budget exactly as independent queries do (which behave byte-identically to before; the contract is additive). The token win lands with the new `quiet: true` flag: the sub-query runs and feeds downstream chains, but its body is omitted from the response — the entry keeps `{index, tool, quiet:true, selected: <value(s) passed on>}` so the chain stays auditable. **Measured** on the test fixture: a chained quiet search→context response is ~33% smaller (ApproxTokens) than the two-call equivalent.
